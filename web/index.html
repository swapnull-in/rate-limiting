Rate limiting · Rate Lab

The front door decides who gets in.

Admission control is the gateway's job, and every design adds it. This lab builds each algorithm from scratch, shows the atomicity race that lets 20 requests through a limit of 5, and covers the two laws that win the interview: fail-open for reads, fail-closed for money, and exact-and-slow vs fast-and-approximate, chosen per endpoint.

Pick a lesson in the sidebar. The one distinction most candidates miss: a rate limit caps the arrival rate; a concurrency limit caps in-flight work — a low rate of slow, expensive requests can still saturate a downstream a rate limiter would happily admit. Mature systems need both.

Fixed window — simplest, with a boundary bug

One counter per fixed window (user:12:04), reset each minute. Trivial and O(1), but a client that straddles the boundary — bursting at the end of one window and the start of the next — sneaks through 2× the limit in a short span.

limit per window5
—

The proof: the counter resets at the window edge, so 10 requests land in a few seconds — 2× the limit of 5 — by putting half at the end of window A and half at the start of window B. Each window saw only 5; together they saw 10. Token bucket and GCRA have no reset instant, so they don't have this bug.

Token bucket — the default

A bucket of capacity B refills at r tokens/sec; each request spends one. It allows a burst up to B (a quiet client banks tokens) but enforces the sustained average r — matching real bursty traffic. Just two numbers per key, lazy refill, no boundary bug. The industry default (Stripe, AWS).

The proof: a full bucket lets a burst of B requests through instantly, then meters to exactly r/sec as tokens drip back. Spam requests → throttled at empty; wait a second → r tokens return and you can spend again. Bigger capacity = burstier; higher refill = higher sustained rate.

Sliding window log — exact, but heavy

Store the timestamp of every request; a request is allowed if fewer than N fall in the last T seconds. Perfectly exact (no boundary bug, true rolling window) — but memory is O(requests) per key, so it dies at scale.

—

The proof: the window (limit 5 per 10 s) slides continuously — old timestamps fall off the left edge and free capacity. It's exact because it counts the true rolling window, not a fixed bucket. The cost is the stored list of timestamps: 0 in memory right now, growing with every admitted request. That O(requests) memory is why you reach for the counter next.

Sliding window counter — the sweet spot

Keep just two integers: the current window's count and the previous window's, then weight the previous by how much of it still overlaps the rolling window. Near-exact with O(1) memory — the production choice for hard per-window quotas (Cloudflare uses it).

position in window50%
—

The proof: the estimate = current + previous × overlap. As the rolling window advances, the previous window's weight decays from 100% to 0%, smoothly aging out its contribution — no boundary jump, no stored timestamp list. It assumes an even spread within a window (the approximation), but with two integers it's within a percent or two of the exact log.

Leaky bucket & GCRA — smooth output, one timestamp

A leaky bucket queues requests and drains them at a fixed rate — perfectly smooth output, but queuing adds latency and it hates bursts. GCRA is "a leaky bucket as a single timestamp" (the TAT): token-bucket behavior with just one stored value and no refill loop — what Redis-Cell implements.

—

The proof: the leaky bucket forces the burst out one-every-500 ms — output is perfectly smooth, but the 6th request waits ~2.5 s (the latency cost). GCRA stores only the TAT (theoretical arrival time): it admits a burst up to a tolerance, then meters to the sustained rate — token-bucket behavior with a single value and no background refill.

Distributed — the atomicity race

One node is trivial; across a fleet the state lives in a shared store (Redis). The trap: read-compute-write from the app races — two gateways read tokens=1 at the same instant and both allow. The fix is atomicity in the store (a Lua script / CAS), not in the app.

The proof: the naive limiter does GET, then INCR as two steps — 20 requests all read the count before anyone writes, so all 20 are allowed (5× over). The atomic Lua path runs the whole check-and-decrement as one indivisible operation in the store, so exactly 5 pass. Use the store's clock inside the script too, never per-node wall clocks.

Exact-and-slow vs fast-and-approximate

Holding a global limit across N gateways is a trade. Central store: exact, but a synchronous hop on every request. Local divided quota: free, but LB skew false-throttles. Local + batch-borrowing: the production answer — borrow 20 tokens at a time, ~1 store trip per batch, a few % overshoot.

strategyallowed / 100store tripsaccuracy

The proof: the central store admits exactly the limit but pays a trip per request. Local divided quota does zero trips but a hot node exhausts its L/N and false-throttles while others sit idle → under-admission. Borrowing hits the store ~once per batch and lands near the limit with a small overshoot. Rate limits protect capacity, not billing — accept ~5% overshoot unless it's a quota.

Layered limits — a request passes every bucket

Limits stack: a request must be admitted by all of per-IP → per-API-key/tier → per-tenant (fairness) → per-endpoint → global (capacity floor). The first layer to deny wins and names itself in the 429. Per-tenant limits are what stop a noisy neighbor from starving everyone else.

—

The proof: each request descends the stack; the first bucket with no tokens denies and names the layer. Hammer tenant A and it's stopped at the per-tenant layer — but tenant B's requests still sail through, because A's throttle is scoped to A's bucket (noisy-neighbor protection). A whale API key is a hot partition: split its bucket into sub-buckets or give it dedicated capacity.

Redis is down — now what?

The #1 failure probe. The answer that separates Staff: fail-open vs fail-closed is a per-endpoint policy, not a global switch. Fail open for user-facing reads (availability beats enforcement); fail closed for auth/payment (enforcement is the security). A conservative local cap covers the gap either way.

—
—

The proof: with the store up, all three enforce normally. With it down, /feed fails open and still serves — you don't take down the read path because the limiter's dependency blinked. /login and /pay fail closed (503) — you must not let an attacker credential-stuff or replay payments freely just because Redis is unreachable. A conservative local cap keeps reads from being truly unlimited. The limiter must never be a single point of failure for the whole API.

The retry storm — when the limiter amplifies load

A 429 is part of the API contract. But naive clients that retry immediately pile their retries on top of new traffic, so the limiter amplifies load instead of shedding it. The fix is exponential backoff + jitter and a Retry-After header so well-behaved clients self-regulate.

The proof: immediate retries accumulate — offered load climbs every tick while the limiter keeps rejecting, the storm feeding itself. Backoff + jitter spreads retries out so offered load stays bounded and the system drains. And shed early: a rejection at the edge (WAF/CDN) costs ~nothing; the same rejection inside the service already spent connection, TLS, auth, and a thread.

Rate ≠ concurrency

A rate limiter caps arrivals per window. A concurrency limiter caps in-flight work. A low rate of slow requests can still saturate a downstream a rate limiter happily admits — because in-flight = arrival rate × service time (Little's Law). Mature systems need both.

The proof: the arrival rate (3/tick) is well within any rate limit, but each request holds a slot for 6 ticks — so in-flight = 3 × 6 = 18 (Little's Law) climbs past the pool of 10 and the downstream saturates. A rate limiter never sees it. A concurrency limiter (a semaphore on in-flight count) holds it at 10, rejecting the overflow — the right tool for a slow downstream.
